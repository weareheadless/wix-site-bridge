## Contract and trust boundaries

- All operations load one v1 site manifest, require the exact `--site` alias, and compare that alias's manifest `siteId` against `WIX_ALLOWED_SITE_IDS`. The manifest binds the connected repository, branch, configured embed IDs, placement and page scope. IDs/URLs do not select a target. The bridge has no project/workspace knowledge identity; that remains a consumer-side mapping.
- Custom Embed API calls use Wix's documented `https://www.wixapis.com/embeds/v1/custom-embeds` API and the documented Wix OAuth token endpoint. The bridge obtains a site-scoped app token from `WIX_APP_ID`, `WIX_APP_SECRET`, and `WIX_APP_INSTANCE_ID`; the app needs `SCOPE.EDITOR.MANAGE_CUSTOM_EMBEDS`. Account API keys, browser cookies, editor internals, undocumented endpoints and user-session identity are not accepted substitutes. Wix CLI publish uses the separately authenticated interactive Wix CLI.
- The package has a bridge version (`0.1.0`) and MCP protocol negotiation (`2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`). The Wix Custom Embeds URL is not versioned by this project; do not imply that the package/MCP version pins Wix's upstream API schema.
- `--apply` gates local artifact/snapshot writes, Custom Embed writes and restore. CLI `publish --apply` and `release --apply` invoke Wix CLI and require its interactive confirmation. MCP publish/release `apply=true` returns `requires-local-terminal`; it does not silently publish. A custom embed update can affect the next live render immediately. This interface is not a safe queue or an exact approval receipt by itself.

## Phase receipts and recovery

The snapshot is durably written before code publish, but the `publishing` receipt is only built in memory. `release-operation.mjs` first writes the receipt after publish fails (line 80) or after the embed phase completes/fails (line 105). A process crash after Wix has published code but before that write can therefore leave no release receipt, even though the snapshot exists. Recovery must treat that as an evidence gap: inspect the saved snapshot, current source and Wix state, then establish the publish outcome before retrying; do not assume the missing receipt means publish did not happen. After a receipt is written, it records `publish-failed`, `complete`, or `partial` phase results. Never repeat the previous plan blindly or overwrite an intervening Wix edit. `restore` compares current content hashes before writing: an embed still at the snapshot's `beforeHash` is a no-op, one at the release's `desiredHash` is eligible for restore, and any other hash blocks the entire restore. Eligible writes use the current fetched Wix revision as a CAS. Restore covers embeds only; code rollback is a separate Git revert and Wix CLI publish. A disconnected/lost response can still leave an uncertain external effect and requires fresh reads before any retry.

The first adapter contract can therefore promise: explicit target identity, read-only inspection/plan, private deterministic preparation, documented Wix Custom Embed read/write with revision checks, distinct interactive code publication, and phase receipts with documented recovery limits. It cannot promise one atomic Wix release, an unattended MCP publish, arbitrary snippet HTML updates, a generalized Wix CMS writer, or visual/readback correctness beyond the stated checks.
